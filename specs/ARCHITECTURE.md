## System topology

Per PRD Section 9.1 — everything runs on a local machine except the holder app, which runs on the iPhone 14 Pro, communicating over the local network. Nothing is hosted externally (TR-14).

| Component | Role | Stack |
| --- | --- | --- |
| Circuits | Credential commitment, eligibility predicates, nullifier, leaf-binding proof | circom 2.2.3, circomlib, snarkjs |
| Local chain | EVM dev chain hosting the contracts | Anvil (Foundry) |
| On-chain contracts | Proof verification, root and nullifier registries, per-offering policy | Solidity; verifier generated by snarkjs |
| Holder app | Credential storage, on-device proving, consent UI, measurement | SwiftUI + mopro (Rust/UniFFI) |
| Measurement | Structured performance records | Node (collector) + Python stdlib (analysis) |
| Issuer service | Issuance, valid-set tree, revocation, sanctions and jurisdiction roots, root publication | Node.js + TypeScript |
| Platform backend | Offering policy, presentation requests, proof intake | Node.js + TypeScript |
| Platform frontend | Offering UI, QR presentation, result display | React + Vite |

Trust boundaries (what crosses which boundary, and what never does) are defined in `credential-protocol.md` Section 8.3 — not repeated here to avoid drift between copies of the same table.

## Circuits: circom + Groth16 + BN254

**Choice:** circom 2.x for circuit authorship, Groth16 as the proving system, BN254 as the curve (TR-1).

**Why Groth16 and BN254:** Groth16 produces the smallest proofs and cheapest verification of the mainstream proving systems — relevant because verification happens on-chain, where every byte and every opcode costs gas. BN254 specifically because Ethereum has native precompiles for it (`ecAdd`, `ecMul`, `ecPairing`) — a different curve would mean implementing pairing arithmetic in Solidity itself, orders of magnitude more expensive.

**Why circom:** a mature toolchain for this stack. `circomlib` provides the Poseidon, comparator and Merkle building blocks, `snarkjs` produces the proving keys and the Solidity verifier, and mopro compiles circom circuits for iOS.

**Why Poseidon:** a hash designed for arithmetic circuits, far cheaper in constraints than SHA-256 or Keccak. A single Poseidon call over two inputs costs 517 constraints (measured in [`../circuits/BASELINE_RESULTS.md`](../circuits/BASELINE_RESULTS.md)).

**Tradeoff accepted:** Groth16 needs a circuit-specific trusted setup (TR-4); PLONK-family systems avoid this at the cost of larger proofs and costlier verification. The first phase reuses the public Hermez Powers-of-Tau, and only the circuit-specific second phase runs locally, a negligible cost for a research PoC. Groth16 over BN254 is also not quantum-safe (PRD Section 11 L9).

## Native mobile proving: mopro (Rust + UniFFI)

**Choice:** mopro for on-device proving. Circuits run through a compiled native path: `rust-witness` transpiles the circuit's WASM to native code at build time, `arkworks` does the Groth16 proving, and UniFFI-generated bindings expose it to Swift.

**Why:** an iOS app is one compiled, sandboxed binary with no Node.js or script runtime inside it, so the desktop `snarkjs` path cannot run there. mopro orchestrates the native path in place of hand-rolled cross-compilation and FFI work, and builds on existing libraries throughout. Setup steps: [`../TOOLCHAIN.md` Sections 1–6](../TOOLCHAIN.md) (desktop) and [Section 8](../TOOLCHAIN.md#8-ios-toolchain) (iOS).

**Tradeoff accepted:** the proving call is opaque. Witness generation and proving run as one FFI call with no timing or progress hooks, so measurement records report the combined time under `proving_ms` and the holder app can show an estimate of proving time but not live progress.

## On-chain verification: Foundry + Solidity + Anvil

**Choice:** Solidity contracts built, tested and deployed with Foundry (forge/anvil/cast) on a local Anvil chain.

**Why:** `snarkjs` generates the verifier in Solidity and the EVM is the verification target (TR-9). Foundry is fast, runs Solidity tests directly against an in-memory EVM, and ships as native binaries, so it adds no third runtime next to Rust (mopro) and Node (circuits tooling).

**Structure:** the contracts are split by who owns the data. `EligibilityRegistry` holds the issuer's roots, `NullifierRegistry` the consumed nullifiers, and `OfferingPolicy` each offering's policy and the proof check through the generated verifier. Details: `specs/phase-3/verification-infrastructure.md Section 3`.

## Measurement: Node collector + Python analysis

**Choice:** no framework on either side. The collector (`measurement/collector/server.js`) uses Node's built-in `http` module with no dependencies, and the analysis (`measurement/analyze/analyze.py`) uses only the Python standard library.

**Why:** the collector only receives JSON records over local HTTP, deduplicates them by `record_id` and appends them to an NDJSON file, so a framework such as Express would add attack surface and install steps for no benefit. Likewise pandas adds install friction without adding capability at this data volume (dozens to low hundreds of records). Fewer dependencies also serve clean-checkout reproducibility (TR-13).

**Durability:** the app persists each record on-device first and syncs afterwards, retrying until the collector acknowledges, so a measurement run survives an unreachable collector. Details: [`measurement-pipeline.md` Section 3](phase-1/measurement-pipeline.md#3-on-device-persist-then-sync).

## Services: issuer service and platform backend/frontend

- **Issuer service** — Node.js + TypeScript on Node's built-in `http` module (no framework), `better-sqlite3` for credential and tree state, `circomlibjs` for Poseidon, `snarkjs` to verify leaf-binding proofs, and in-house Merkle trees (valid-set and jurisdiction trees, plus an indexed tree for sanctions). It publishes roots through `viem`, signed by an on-chain account key.
- **Platform backend** — Node.js + TypeScript, `viem` for chain interaction; generates presentation requests and submits verification transactions.
- **Platform frontend** — React + Vite, QR rendering for presentation requests; reads verification results from the chain.

**Why:** the same runtime and the same minimal-dependency approach as the rest of the Node tooling (circuits, measurement collector), with no reason to add a second backend language for services that are mostly HTTP APIs and chain I/O.

## Terminology: "witness"

This term is reused across the ZK/blockchain space for genuinely different things — worth being precise, since it appears constantly in this codebase (`witness.wtns`, `generate_witness.js`, `witness_gen_ms`). In this project (circom/snarkjs/Groth16), a **witness** is the complete assignment of values to *every* signal in a circuit — private inputs, public inputs, and every intermediate computed wire, not just "the private data." It's a concrete file, produced from raw inputs by the circuit's compiled witness calculator, and it's what the prover actually consumes to build a proof.

For contrast: Cardano uses "witness" for a transaction's signature/authorization data (the `witness_set` — signatures, scripts, redeemers — a sibling field to the transaction body and metadata, not related to circuit computation at all). Midnight's Compact language uses "witness" for off-chain TypeScript functions that *supply* private data to a circuit — closer to writing this project's `input.json`, but as executable code rather than a static file; the full internal assignment vector (the sense this project uses) is built later, inside their proof server, and isn't what their docs call "witness."

**Within this project specifically:** the same collision risk exists internally, between the circom sense above and the standard cryptographic term for a Merkle inclusion proof — the sibling hashes and left/right indices needed to walk a leaf up to a root, often called a "Merkle witness" in the wider literature. `credential-protocol.md`, `PRD.md`, and `circuits/merkle-baseline/template.circom` all use **"Merkle path"** for this instead (matching the actual circuit signal names, `pathElements`/`pathIndices`), reserving "witness" exclusively for the circom/Groth16 sense everywhere in this repo's docs. When writing about Merkle inclusion or non-membership data, use "Merkle path", not "Merkle witness."
